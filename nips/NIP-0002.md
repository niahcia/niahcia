# NIP-0002: Canonical Encoding, Hashing, and Signatures

- Status: Draft
- Type: Core
- Created: 2026-09-28

## Abstract

This NIP defines the initial canonical data foundation for NIAHCIA Protocol v1.

It establishes:

- deterministic CBOR-based NIAHCIA Canonical Encoding (NCE/1)
- numeric protocol object-type identifiers
- Keccak-256 protocol hashing
- explicit network and purpose domain separation
- stable versus content-derived identifier classes
- secp256k1 controller/protocol signatures
- replay-protection requirements
- EIP-712 compatibility for wallet-facing signing

## Motivation

NIAHCIA spans EVM contracts, Rust chain software, AI workers, service nodes, explorers, websites, storage systems, and future independent implementations.

These components require one deterministic answer to:

> What exact bytes identify this object, and what exact digest did this participant sign?

Without a canonical encoding and signing foundation, implementations can disagree because of JSON ordering, whitespace, Unicode representation, optional fields, integer formatting, map ordering, or signature context.

## Design decisions

### Deterministic CBOR

NCE/1 uses deterministic CBOR with stricter protocol rules:

- numeric field keys
- definite lengths only
- no unassigned tags
- no duplicate map keys
- shortest integer representations
- no protocol-critical floating point
- explicit optional-field behavior

### Keccak-256

Keccak-256 is selected for protocol identity because it is native to the EVM and efficient to verify from Solidity.

### Domain separation

Object IDs and signatures bind:

- NIAHCIA protocol identity
- purpose/domain
- network identity
- canonical payload

### Stable and content-derived identity

Objects whose identity must survive updates use stable registry/nonce-derived IDs.

Immutable definitions use content-derived hashes.

### Signatures

secp256k1 is the v1 protocol signing default for controller/economic authorization.

P2P transport identity is intentionally separate from protocol authorization.

## Backward compatibility

This NIP defines the first protocol serialization suite; there is no prior stable production encoding.

Future suites must use explicit versioning and MUST NOT silently reinterpret v1 bytes or identifiers.

## Security considerations

Canonicalization rules are security-sensitive.

Implementations must reject ambiguous/noncanonical encodings during verification rather than normalizing attacker-controlled alternate encodings after the fact.

Independent test vectors are required before this NIP can move beyond Draft.
